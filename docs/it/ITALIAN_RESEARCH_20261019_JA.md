## 01 開発判断

イタリア語版KUMIHANは、標準的な綴りを守る機能と、媒体・組織・ブランドに合わせて組み方を選ぶ機能を分けて開発する。引用符、語末の改行、価格表示、呼びかけの人称には複数の妥当な方式がある。一つの「イタリア式」へ統一すると、正しい文章や既存のブランド表現まで壊す。

初版の価値は、イタリア語の原稿を保護しながら、本文・見出し・UI・文書の違いを理解して提案できることに置く。見た目の改善と意味の変更を別々に記録し、未確認の描画や読み上げを合格にしない。

### 優先順位

| 優先 | 初版で扱うこと | 判断理由 |
| --- | --- | --- |
| A | アクセント、アポストロフィ、引用・固有名・数値の保護 | 意味や正式表記の破壊を先に防ぐ |
| A | 本文、見出し、UI、報告書、スライドのプロファイル | 同じ組み方を全媒体に流用しない |
| A | it-ITを主対象とし、it-CHと機関別書式を識別 | 言語と地域と編集方針の混同を防ぐ |
| A | 正例と反例を含む検証ケース、根拠付きの指摘 | 正しい原稿を誤って直さないことを評価できる |
| B | it-CHの詳細プリセット、分綴辞書、支援技術の環境別確認 | 初版の適用範囲を確かめながら広げる |
| B | ブランド別文体、フォント機能、段落の高度な調整 | 実案件と実測環境がそろってから精度を高める |
| 採用しない | 特定の書体や色をイタリア語全体に強制する機能 | 言語品質の根拠がなく、表現の幅を狭める |
| 採用しない | 引用符、人称、価格、意味を無条件に置換する機能 | 正当な別解や保護対象を破壊しやすい |

### 判断を変える主要な発見

Cruscaはアポストロフィ直後の改行を許容している。見出しで回避したい場合も文法違反とは区別する。[L04]

引用符の階層は同じボローニャ大学の資料でも異なる。CISUIはcaporaliを外側に使い、別の論文規定は英式二重引用符を外側に使う。[L12][L13]

Designers Italiaは行政のUIに平易な表現やtuを推奨する。一方、商業サイトには大文字の見出しや複数の人称を使った文言が見られる。行政の方式を全ブランドへ強制しない。[U01][U02][U24][P06]

本報告書は調査と設計提案である。規則案・検証ケース・初版の工程を開発へ渡せる形に整理した。

## 02 根拠の使い方と適用範囲

### 三つの根拠を分ける

| 区分 | 意味 | 例 | KUMIHANの扱い |
| --- | --- | --- | --- |
| 言語上の規範 | 標準的な綴りや語法の説明 | qual è、po’、perché | 対象と文脈を確定して修正候補を示す |
| 編集方針 | 出版社、機関、ブランドの取り決め | 引用符階層、時刻、見出しの大文字 | 選択された方式への適合を判定する |
| 設計提案 | 実例や用途から導く改善 | 行長、意味単位の改行、情報階層 | 理由と代替案を示し、原稿変更と分離する |

「公式資料」はその適用範囲まで確認する。EUやスイス連邦官房の編集規定は当該組織の文書を整える規定であり、民間ECやポスターすべての表記を決めるものではない。[L14][L15]

### 確認の種類

文献確認は原稿や仕様の判断根拠となる。図版視認は公開画像の形・色・情報配置の観察を意味する。テキスト抽出はページ上の文言を確認した状態であり、画面の行折返しやCSSを実測した状態ではない。限定実測は記載したランタイムと条件に限った結果である。

本調査では言語資料、発行主体の編集規定、制作当事者の作品紹介、現地ブランドの公式サイト、W3C・Unicode・ECMAの技術資料を用いた。検索結果だけの文言は本文確認と分けた。作品年、資料の更新時点、取得日を混同しない。

### 設定は独立した軸にする

| 設定 | 内容 |
| --- | --- |
| language と locale | イタリア語か、対象市場まで特定できるか |
| medium | Web記事、LP、UI、文書、スライド、短いコピー |
| content role | 見出し、本文、引用、数値、商品名、コードなど |
| house style | 引用符、日付、数値、敬称の指定 |
| source policy | 原稿をそのまま保つ範囲と編集可能な範囲 |
| evidence | 仕様確認、描画確認、意味確認の各状態 |

この構造はKUMIHANの開発提案である。既存版のコードや配布構造との共通化は、実装開始時に現在のリポジトリを照合して決める。

## 03 アクセントと文字データ

### éとèを区別する

イタリア語ではアクセントを装飾扱いにしない。perchéとcaffèのように語によって種類が異なり、大文字にも保持する。ÈをE'で代用する表記は通常本文の修正候補となる。[L02][L14]

| 確認項目 | 自作例 | 判定上の注意 |
| --- | --- | --- |
| 鋭アクセント | perché、né、PERCHÉ | 全てを重アクセントへ変換しない |
| 重アクセント | caffè、città、più、È | 大文字の上端をクリップしない |
| 語の意味 | e / è、da / dà、si / sì、te / tè | 文字列だけでは置換しない |
| 短縮 | un po’ | 河川名Poと区別する |
| 標準綴り | qual è | 引用や綴りの解説中は原文を保つ |
| 別解のある表記 | sé stesso / se stesso | 編集方針を確認して提案する |

qual èはアポストロフィを付けない標準綴りとして扱う。po’はpocoの短縮であり、pòと混同しない。いずれも歴史的資料の忠実な引用や人名まで一括修正する根拠にはならない。[L01][L03]

sé stessoを推奨形にしても、se stessoを直ちに誤りと判定しない。参照資料間で扱いが異なる。Se stessi meglio, verrei.のような条件文まで変更すると意味を壊す。[L02][L14]

### 表示文字と機械文字を保護する

通常の表示文では組版用のアポストロフィを選べる。一方、JSON・JavaScript・SQL・URL・識別子などの直線引用符は構文や照合キーの一部である。表示用置換の対象から外す。

Unicodeでは合成済みのèと、eに結合アクセントを付けた表現を正規化の枠組みで扱う。文字列の分割では見かけの一文字とコードポイント数が一致しない場合がある。[T01][T02]

KUMIHANでは元のバイト列と編集後の表示文字列を区別する。入力を無断でNFC化して「原文を保持した」と報告しない。変更が必要な処理だけを選び、差分を残す。文字幅計算や切詰めも結合文字を壊さない方法で実装する。

### フォント確認用の自作文字列

à è é ì ò ù À È É Ì Ò Ù

Caffè e tè perché ogni parola è diversa

L’acqua dell’architettura  «Forma»  “Spazio”  ‘voce’

€ CHF 0123456789 1º 1° 20 °C

上記は字形確認用の作例であり、全てを同じ書式へ統一する指示ではない。特に序数のº、度の°、引用符、桁区切り用のアポストロフィは役割を見て判定する。

## 04 引用符と句読点と大文字

### 引用符の方式を指定可能にする

| 方式 | 構造例 | 根拠と扱い |
| --- | --- | --- |
| caporaliを外側にする | «Una forma “aperta”» | CISUIの編集規定を参考にできる |
| 二重引用符を外側にする | “Una forma ‘aperta’” | 別の大学論文規定にも採用例がある |
| 忠実な引用 | 引用元の記号を保持 | 著者の表記を再現する必要を優先する |
| UIの直接表示 | 引用符を付けないラベルも含む | 文書用の引用符規定を流用しない |

構造例は本報告の自作である。初期設定が未指定のときは、原稿内の一貫した方式を保持する。複数方式の混在も、入れ子・引用元・多言語部分を確認してから指摘する。[L12][L13]

EUの規定では引用符の内側にスペースを入れない。フランス語の組版をそのまま移して« testo »へ統一する設定は避ける。ただし引用元やブランド指定がある箇所は別に扱う。[L15]

### 句読点の帰属を読む

文末の句点を閉じ引用符の外に置く一般的な説明はあるが、原著を忠実に転記する引用では内部の句点を残す場合がある。疑問符や感嘆符も、どの発話・文に属するかで判断する。句点を全て内側または外側へ移動する処理は作らない。[L07]

通常の文では句読点の直前に機械的な空白を置かず、後ろの語との区切りを整える。省略符号、列挙の終止、ダッシュの長さと空白は媒体の編集方針として定義する。三点を含むURLやバージョン番号まで変換しない。[L12][L13]

ハイフン、挿入句のダッシュ、範囲、負号は区別する。資料によって範囲記号の選択も異なるため、見た目の類似だけで一括置換しない。[L13][L14]

### 見出しと正式名を分ける

一般のイタリア語の見出しに英語式のTitle Caseを機械的に適用しない。月・曜日は通常小文字とする一方、文頭、祝祭名、正式名称には別の判断が必要である。ONUとOnuなどの頭字語や敬称も指定方式を確認する。[L10][L11]

大文字だけのポスターやブランドのナビゲーションはデザインの選択となり得る。全大文字を使ったことだけで言語エラーにしない。問題はアクセントの欠落、読みにくい長文への波及、意味の不明確さなどに分けて記録する。

d eufonicaのed・ad・odも文体の層で扱う。同母音の連続は一つの目安だが、ad esempioなどの定着表現や後続音の例外がある。同母音だけを条件にdを挿入・削除しない。[L05][L06]

## 05 改行と段落組版

### アポストロフィ直後を一律に禁則化しない

Cruscaの説明では、dell’の直後で次行へ送る方法は許容される。行末を避けるために省略した母音を復元する方法は不適切である。この違いはイタリア語版の重要な反例となる。[L04]

KUMIHANでは、本文の許容される折返しを文法エラーにしない。短い見出しで語のまとまりが読み取りにくい場合は、幅、文字サイズ、行数、字間の順に検討する。語の一群だけを改行禁止にする選択は可能だが、段落全体をnowrapにして横溢れを作らない。

### 音節分割と意味の切れ目を別々に見る

イタリア語の分綴には二重子音、sと後続子音、二重音字、母音の組合せなどが関わる。複合語では語源上の境界を使う別解もある。数個の正規表現だけで完全な判定器を作らない。[L08][L09]

CSSの自動分綴には言語指定と対応する言語資源が必要である。hyphens:autoを記述しただけでは、対象ブラウザでイタリア語の辞書が働くことを証明できない。[U10]

### 媒体別の初期方針

| 対象 | 初期方針の提案 | 調整時に見ること |
| --- | --- | --- |
| Webの長い本文 | 左揃えと自然な折返しから始める | 行長、段落間隔、フォント幅 |
| 印刷物の長い本文 | 両端揃えも選択可能 | 分綴、語間の広がり、白い筋 |
| 短い見出し | 語と意味のまとまりを優先 | 修飾語と名詞、前置詞と名詞句 |
| UIラベル | 操作名を読める形で保持 | 狭幅、文字拡大、複数行のボタン |
| 数値と単位 | 短いまとまりを保護 | 横溢れ、負号、単位の意味 |
| URLと識別子 | 必要箇所のみ局所的に折返す | コピーした値が元と一致するか |

上表はKUMIHANの提案値・方針である。全媒体の強制規範ではない。

見出しのtext-wrap:balanceは各行の長さを整える機能であり、文章の意味を解析して区切る機能ではない。意味の切れ目を改善したという判定には、実際の改行を見た上での確認が必要となる。[U11]

文書では見出しと次の段落、表の行、図とキャプション、脚注を一緒に扱う。最終行が短いだけで語句を削除せず、孤立行・段落全体の形・読む順番を併せて判断する。

## 06 地域別の数値と日付

### localeと編集規程は別の設定

Unicode CLDRの参照データにはitとit-CHの小数記号、桁区切り、通貨位置、短い日付の差がある。これらは標準的な表示データであり、出版社や行政機関の全文書規程と同じものではない。[U05]

スイス連邦官房のイタリア語規定では、一般小数と貨幣小数で記号を使い分け、5桁以上を保護スペースで区切る方式を示す。EUの編集規定にも固定スペースによる3桁区切りがある。これをすべての民間UIへ一般化しない。[L14][L15]

### 限定実測

以下は本調査で実行した値である。環境はNode.js v24.19.0、ICU 78.3、CLDR 48.0。数値はIntl.NumberFormatの既定表示、通貨はEURまたはCHFを指定。割合は最大小数1桁とした。ブラウザの結果は含まない。[O01]

| 元の値と用途 | it-ITの実出力 | it-CHの実出力 |
| --- | --- | --- |
| 1234.56 一般数値 | 1234,56 | 1234.56 |
| 12345.67 一般数値 | 12.345,67 | 12'345.67 |
| 12345.67 通貨 | 12.345,67 € | CHF 12'345.67 |
| 0.125 割合 | 12,5% | 12.5% |
| 2026年10月19日 長い日付 | 19 ottobre 2026 | 19 ottobre 2026 |

通貨の空白はU+00A0、今回のit-CHの桁区切りはU+0027だった。外見の似た記号を想像で固定しない。日付の実測入力は2026-10-19T12:00:00Z、dateStyleはlong、timeZoneはEurope/Romeである。

参照したCLDRチャートは49で、実測ランタイムは48.0だった。ECMA-402も実装やデータ更新による差を扱う。固定文字列のテストではバージョンとオプションを記録し、異なる環境に同じ文字列を無条件で要求しない。[U05][U06]

### 商業表示を誤りと決めつけない

Alessiの公式ページには、抽出テキスト上で€を前に置く価格が見られた。これはCLDRのイタリア向け既定パターンとの差であり、それだけで誤記とは言えない。[U23]

元データが数値なら表示層でローカライズする。既存の1.234という文字列だけを見て、1234、1.234、小数、商品番号のどれかを決めない。通貨、値、符号、丸め、精度、項目の意味を先に確認する。

パーセントや単位の空白にも技術文書・機関規程・ECの違いがある。選択した方式への整合性を判断し、価格・税率・寸法を体裁の都合で変更しない。日付の区切り記号、先頭ゼロ、年の桁数も用途の設定として持つ。

## 07 フォントと情報階層

### 書体は役割から選ぶ

Designers Italiaの公式ページはTitillium Webを基本書体、Loraを長い本文、Roboto Monoを技術情報の用途に示す。Titillium Proは参照時点では実験段階の説明だった。この構成は行政サービスの実例として有用である。[U04]

| 役割 | 選択の基準 | 避けること |
| --- | --- | --- |
| 長い本文 | 読みやすい字形、十分な太さ、斜体、適切な語間 | 造形の細さだけで書体を決める |
| 見出し | 内容の性格と文字数、アクセントの高さ | 小さなボックスに入れるための極端な圧縮 |
| UI | 小サイズの識別性、太字、数字、fallback | ブランドの装飾書体を入力欄まで広げる |
| 表の数字 | 数字の幅、桁揃え、符号と通貨の識別 | 空白文字で桁を合わせる |
| ポスター | 情報の優先順位と距離、短い文のリズム | ポスターの字間を本文へ流用する |

OpenTypeのtabular-numsやordinalなどは、フォント側の機能に依存する。CSSを指定しただけで該当字形が存在するとは限らない。[U12]

CASTやCollletttivoの事例は、イタリアの制作文化にも用途の異なる書体があることを示す。フォントの制作国は採用の必須条件にしない。候補ごとに文字集合、太字・斜体、機能、Web利用と再配布の条件を確認する。無料で取得できることと、あらゆる用途に同じ条件で使えることを同一視しない。[V11][V12][V13][V14]

### 数値は出発点として提示する

KUMIHANのWeb本文では16〜18 CSS px、行高1.45〜1.65、行幅55〜75chを試し始める候補にできる。いずれも本報告の設計提案であり、正書法やWCAGの必須値ではない。対象フォント、文章、端末に合わせて調整する。

.italiaには1行75文字以内の推奨があるが、CSSの75chは比例幅の75文字を意味しない。字間を変えれば実際の行長も変わる。設定値だけで合格にせず、描画された文章を確認する。[U04]

見出し、本文、キャプション、数値、リンクを役割で分ける。階層はサイズだけで作らず、太さ、位置、余白、情報順序を組み合わせる。強い書体を一つ使えば情報設計が完成するわけではない。

## 08 グラフィックと編集の実例

今回の事例から採用するのは、内容・読者・媒体に応じて文字の役割を変える方法である。書体、色、余白、装飾を「イタリア語の標準外観」として固定しない。以下では制作主体が説明する事実、公開図版で見えたこと、KUMIHANへの提案を分ける。

### 歴史的な表現を現在の規則と分ける

Salone del Mobileの1961年・1994年の公式ポスターと2026年のキャンペーンは、時代による表現の違いを比較する参照とする。過去の一作から現在のブランド全体に共通する外観を決めない。キャンペーンの英語名も、そのまま使用される正式名称として扱う。[P09][P03][P02]

| 1961年 [P09] | 白黒の図像と黄色い椅子、イベント情報を組み合わせる | 主題を伝える図と、開催情報の役割を分けられるか |

### 08.1 Archive and the City — studio FM milano、2025

**事実：** アーカイブと都市の構造を扱う展示。FMが展示とグラフィック、Density Design Labが可視化、CASTのStefano Cremisiniが書体を担当した。**観察：** 黒い展示壁に白い見出し、伊英の本文、地図、関係図が並ぶ。**提案：** データや分類をビジュアルの材料にし、本文と図の読取り方を分ける。展示面積を前提とする高密度の図を、一般LPの装飾へ転用しない。[V01]

### 08.2 Campari BOLD! — studio FM milano、2024

**事実：** Campariの文字表現を扱う展覧会。制作説明はMunariの1964年の広告を着想源に挙げる。**観察：** 公開ポスターモックは極太のBOLD!を大きな面として扱い、補足情報を中に収める。**提案：** 語の意味を造形の理由にする。ただし文字の分解や変形を本文へ広げない。掲載モックの日付は公式開催説明と一致しないため、会期の根拠にも現地設置の証拠にも使わない。[V02]

### 08.3 Cassina Identity System — studio FM milano、2014

## 09 ウェブサイトとブランドの観察

ウェブ調査では文言・資料・掲載作品と、サイトの動作を分けて扱う。今回の制作事例は公式に掲載された資料の確認であり、全画面の描画品質やアクセシビリティを認定したものではない。

### 09.1 サイト本体から確認した範囲

| 対象 | 確認した事実 | 開発への提案 | 未確認の範囲 |
| --- | --- | --- | --- |
| Triennale [V15] | 抽出本文にイベント・訪問・購入等の案内と、言語の導線がある | 来訪目的で情報を分類し、言語選択を識別できる構造にする | 画面幅別の配置、フォーカス、読み上げ、実効CSS |
| MAXXI [V16] | 展覧会・イベント・教育等の分類を確認。取得HTMLには説明的なaltと空altが併存 | 画像の用途を確認して代替テキストの要否を決める | 空altの妥当性、画像の装飾性、支援技術での実際の扱い |
| studio òbelo [V17] | 公開HTMLのメタ説明と埋込み作品データを確認。通常の本文抽出では情報がほぼ出なかった | テキストを取得できた範囲と、見た目を確認できた範囲を記録する | 全体の閲覧体験、動作、SEO評価、アクセシビリティ適合 |

本文抽出の情報量だけでサイトを良否判定しない。空altには装飾画像など正当な用途があり、反対に長いaltがあるだけで適切とも限らない。最終的な判定には画像の目的と実際の操作・読み上げの確認が要る。これは今回の静的確認から生じる検証課題である。[V16][V17]

### 09.2 ブランドの表現とイタリア語の正しさ

Euroluceの案内は伊英を併記し、Artefieraには英文の手書きメッセージがある。Nan Goldinのガイドはイタリア語版でも展示名を英語で保持している。こうした正式名称や対象読者に合わせた表現を、翻訳漏れやイタリア語の誤りとして自動修正しない。[V04][V05][V09]

KUMIHANでは本文言語、正式名称、引用、ブランドの声を別に指定する。全大文字・英語・独自表記を見つけたときは、その役割を確認する。変更案は、正字法上の修正と、ブランドに対する編集提案に分けて示す。

「AIらしいデザイン」の抑制も外観の禁止リストだけで扱わない。今回の事例には立体化、粒子、輪郭文字、強い色がある。採用を検討するときは、主題、情報の分類、ブランド継続、読取り距離への貢献を説明する。理由のない装飾を減らす方針と、表現の多様性を保つ方針は両立する。[V04][V05][V07][V08]

### 09.4 根拠を確認できていないこと

サイト全体のモバイル表示、200%拡大、キーボード操作、スクリーンリーダー、動きの抑制設定への対応は未検証である。画像から正確なポイント数・字間・CSS値・書体名を推定確定していない。アニメーションの元資料に言及した事例も、今回の目視は記録した静止画の範囲に限る。

公式の書体紹介と字形見本は確認したが、採用候補のフォント実体を用いた必要文字の網羅、OpenType機能、OS・ブラウザ別表示は確認していない。読取り速度や理解度への効果も測定していない。各事例からの改善案は設計提案であり、既存KUMIHANの実装に対する検証結果ではない。

## 10 イタリア語のコピーと操作文

### 誰に何を伝えるかを先に決める

コピーを整える際は、文章の役割を先に確定する。展覧会の見出しは関心を引き、商品説明は特徴を伝え、フォームの文言は操作を助ける。すべてを短い命令文へ変える必要はない。見た目を揃えるために説明を削る前に、その情報がどの判断に必要なのかを確認する。

Designers Italiaは行政サービスに直接的なtuを推奨し、利用者の状況に合わせてトーンを変えるとしている。KUMIHANでは行政UIの参考にしつつ、既存のブランド文体や正式な個人宛て対応のLeiも保持する。複数の読者に呼びかけるvoiと、個人に操作を促すtuを同じものとして検出しない。[U02]

人称の整合性は画面や文書の役割ごとに判断する。たとえばキャンペーンが来場者全体へ語りかけ、予約画面が一人の利用者に説明する構成は成立し得る。引用、作品名、メールの宛先まで含めた単純な語尾置換は、文体を整える処理として不十分である。

### 現地サイトは使い分けと例外の両方を示す

Alessiの公式ページでは「Ridefinisci il tuo rituale del caffè」という情緒的な見出しと、購入の操作を示す文言が使い分けられている。KUMIHANが学ぶべき点は、見出しとボタンに異なる仕事を与えることである。[U23]

Moleskineには複数の読者に向けた見出しと、個人へ選択を促す「Scegli la tua」が併存する。人称の出現数だけで不統一と決めず、誰に向けたどの位置の文言かを読む必要がある。[U24]

Cassinaの現行イタリア語ページでは英語の見出しや全大文字のUIを確認した。トップページのCTAは抽出結果で「SCOPRI DI PIU'」となっていた。これは現地で使われる表記の観察であり、アポストロフィによるアクセントの代用を標準的な綴りとして推奨する根拠にはならない。[P06]

同社の製品ページには「CONTATTA UN CONSULENTE CASSINA」という具体的な操作文がある。短さだけを優先して対象を削ると、次に何が起きるか分かりにくくなる。[P08]

以上は公開ページの抽出テキストを確認した結果である。画面上の大文字変換、文字サイズ、改行位置、操作後の挙動まで実測した結果ではない。

### 操作文は結果を予測できるようにする

.italiaは動詞から始まる具体的なCTA、消えない記入補助、問題と修正方法を説明するエラーを示している。行政向けの実用的な手本として参照できる。[U03]

KUMIHANの提案では、ボタンの名称をその操作と結び付ける。エラーでは入力のどこをどう直すかを伝え、原因が未確定なら通信障害や利用者のミスと断定しない。成功文は、実装が完了を確認できる時点で表示する。「数秒」「完全」「必ず」などの語を加える場合は、実際の根拠が必要となる。

本文の分かりやすさを高めるために、手続き名や正式名称を必要以上に崩さない。先に利用者が必要とする説明を置き、正式名称を補足する構成も検討する。専門家向けの内容では専門語を残す方が明確になる場合もある。

包摂的な表現では、特定の性別を前提としにくい構文への言い換えを提案できる。ただし組織の規程、本人の希望、著者の方針を確認する。.italiaとスイス連邦のガイドは対象が異なるため、一つの方針へ統合しない。[U01][U25]

schwa、アスタリスク、男女併記などを著者の指定なしに追加・削除しない。読み上げの可否も使用する支援技術と音声を確認して判断する。字形が表示できたことと、自然に理解できる読み上げになったことは別の確認である。

| 保存完了 | Preferenze salvate. | 短く状態を伝える。保存完了が確認できた場合に使う |
| 検索結果なし | Nessun evento corrisponde alla ricerca. Prova con un’altra parola. | 結果と次の探し方を伝える |

作例を使った検証では、文字数だけを比較しない。操作の対象が伝わるか、実際の状態と一致するか、狭幅でも重要な語が隠れないかを確認する。文章を短くした結果、利用者が必要とする条件や選択肢が失われていないかも見る。

## 11 画一的な生成表現を避ける評価

### 生成元を推定する判定にしない

KUMIHANが扱う「AIらしいデザインの抑制」は、制作にAIが使われたかを見抜く機能ではない。内容と関係の薄い装飾、役割のない反復、説明不足、操作しにくさを評価し、理由のある表現へ直すための設計方針とする。

特定の外観を一律に禁止すると別の画一化が起こる。立体表現、鮮やかな色、非対称、巨大な文字、手描きの要素はいずれも選択肢になる。今回のEuroluceやArtefieraの事例では、表現の変更が展示の主題、既存のブランド、媒体の使い方と結び付いていた。形だけを取り出して良否を決めない。[V04][V05]

### 五つの問いで理由を確認する

**情報に理由があるか。** 主役の文字や画像は、商品、作品、主題の理解を助けているか。内容を他の案件へ入れ替えても成立してしまう装飾が中心なら、まず情報の選び方から見直す。

**一貫性が役に立つか。** 見出し、本文、価格、注釈、ボタンの役割が区別できるか。同じ役割は揃え、役割が違うところには適切な差を付ける。すべてを同じ大きさのカードへ収めること自体を目標にしない。

**密度が用途に合うか。** 短いキャンペーンに不要な説明を足していないか。比較表や案内文から必要な条件を削っていないか。余白が多いことも情報が多いことも、それだけで品質の根拠にはならない。

**文字の造形と意味が両立するか。** 大きさ、変形、分解、改行が文章の理解を助けるか。見出しに有効な変形が、本文、数値、フォームにも広がっていないか。コピーを画像化した場合は、必要な意味を別の形でも利用できるようにする。

**使い続けられるか。** 長い商品名、新しい日付、別の言語、価格改定が入っても階層が保てるか。手作業の改行や文字ごとの位置調整に依存しすぎると更新が難しくなる。操作文の短さと、結果の分かりやすさも併せて見る。

これらは本報告が提案する評価軸であり、外部の認証基準ではない。最初から点数を合算するより、改善理由が説明できる項目、意味の判断が必要な項目、未実測の項目を分ける。制作意図が不明な表現には質問や代替案を示し、装飾を削っただけで改善と報告しない。

### Webの最小構成案

ページ全体がイタリア語ならルート要素に`lang="it"`を設定し、対象地域を明示する必要がある場合は`it-IT`や`it-CH`を使う。複数言語の文章がある場合は該当範囲の言語も示す。外国語由来の固有名や定着した専門語まで機械的に別言語へ割り当てる必要があるわけではない。[U07][U08][U09]

次は既存のページへ適用する際の考え方を示す短い案である。文章は第10章の作例を短くしたもの、価格は表示確認用の架空値である。コードはブラウザで実行していない。

```html
<section lang="it" class="it-copy">
  <h2 class="it-heading">La forma delle idee</h2>
  <p class="it-body">Disegni, prototipi e oggetti.</p>
  <p class="price">24,00&nbsp;€</p>
</section>
```

```css
.it-body {
  max-inline-size: 68ch;
  line-height: 1.55;
  text-align: start;
  word-break: normal;
  hyphens: manual;
}
.it-body.with-hyphenation { hyphens: auto; }
.it-url { overflow-wrap: anywhere; hyphens: none; }
.price { white-space: nowrap; }
.number { font-variant-numeric: tabular-nums; }
@supports (text-wrap: balance) {
  .it-heading { text-wrap: balance; }
}
```

68chと行高1.55は試し始めるための提案値である。本文幅は実際の字形と文章で調整する。自動分綴は対象環境の辞書を確認した本文へ追加し、長いURL等には局所的な溢れ対策を使う。通常の語を無条件に一文字ずつ切る設定へ置き換えない。[U10]

改行禁止は短い価格のまとまりに限定している。カードや段落全体へ広げず、価格が長くなる場合も別途確認する。表の数字機能は対応フォントで効くかを確かめる。見出しのbalanceは意味を理解して改行する機能ではないため、語句の切れ目は目視する。[U11][U12]

実装ではこの例だけでページ全体が収まると考えず、親コンテナの幅、長い語、入力値、画像、ボタンの高さも確認する。Webフォントを読み込めない条件で、情報と操作が維持されるかも確認する。

### 文書・スライド・データへ移すとき

文書では段落スタイルと文字スタイルを先に決め、空白の連続や改行の連打で位置を合わせない。見出しと次の段落、図とキャプション、表の見出し行をまとまりとして扱う。固定PDFへの書出し後はアクセント、行末、改ページ、脚注を再確認する。元の編集画面で収まっていたことを、別の出力の合格理由にしない。

スライドでは文字を小さくする前に、主張と補足の分け方、図の役割、説明の重複を見直す。意味のある用語や数値を削って文字数を減らさない。イタリア語の短い見出しでも、前置詞と名詞句の位置、強調語と補足の関係を確認する。

データラベルは第6章の地域と編集規程に沿って表示する。数値の丸め、単位の選択、通貨は組版側で勝手に決めない。表の桁を空白で揃える処理や、幅に収めるために精度を落とす処理も避ける。

### 拡大と読み上げの確認を独立させる

Webでは文字200%拡大、320 CSS px相当幅のリフロー、文字間隔の上書きを別のケースにする。上書きは文字サイズに対して行高を1.5倍、段落後の間隔を2倍とし、字間0.12em、単語間0.16emを同時に設定した条件で確認する。これらはサイトの初期スタイルを決める同一の検査ではない。[U13][U14][U15]

読み上げでは、言語・ラベル・エラー・数値の伝わり方を確認し、OS・ブラウザ・支援技術・音声を記録する。KUMIHAN適用後の実装試験は未実施であり、報告書のレイアウト確認とは区別する。

## 13 提案ルールカタログ

以下の40ルールは初版の開発へ渡す提案である。実装済みの機能一覧でも、試験に合格した項目の一覧でもない。判定対象の言語・媒体・役割・編集方針を先に特定し、原稿の保護範囲を確定してから適用する。

## 14 評価用フィクスチャ

48件すべてが開発用の評価案であり、本報告書で評価器やKUMIHANの合格を確認したものではない。F01〜F24は言語判断と原稿保護、F25〜F48は表示・データ・操作の評価に重点を置く。同じ文字列でも、綴りの判断と描画・コピー操作の確認は別の評価である。

入力文は本報告の自作例と、確認条件を示す短い記号列である。期待結果に記した判定語はルール案の処理を指す。評価の実施結果は別に `pass`、`fail`、`needs-review`、`not-checked` で記録する。以下の全フィクスチャの実施状態は `not-checked` とする。

### 完了は設定・挙動・証拠で判定する

初版の完了報告には、少なくとも次を含める。

- **範囲が一致すること。** 説明文、入口の判定、出力例、配布物で対応言語と媒体が食い違わない。it-CHを見つけてもit-ITの数値へ黙って置換しない。

**[O01] Intl.NumberFormat / Intl.DateTimeFormatの実行記録**

実行時刻2026年10月18日21:05 UTC。Node.js v24.19.0、ICU 78.3、CLDR 48.0。it-ITとit-CH、数値1234.56・12345.67、通貨EUR・CHF、割合0.125を使用した。一般数値は既定オプション、通貨はstyleとcurrency指定、割合はstyle:percentとmaximumFractionDigits:1を指定した。日付入力2026-10-19T12:00:00Z、dateStyle:long、timeZone:Europe/Rome。結果は第06章に掲載した。

再現用コードは以下のとおり。実行結果の一致には同じ環境とオプションを用いる。

```js
for (const locale of ['it-IT', 'it-CH']) {
  const currency = locale === 'it-IT' ? 'EUR' : 'CHF';
  const number = new Intl.NumberFormat(locale);
  const money = new Intl.NumberFormat(locale, {
    style: 'currency', currency
  });
  const percent = new Intl.NumberFormat(locale, {
    style: 'percent', maximumFractionDigits: 1
  });
  const date = new Intl.DateTimeFormat(locale, {
    dateStyle: 'long', timeZone: 'Europe/Rome'
  });
  console.log(locale, number.format(1234.56),
    number.format(12345.67), money.format(12345.67),
    percent.format(0.125),
    date.format(new Date('2026-10-19T12:00:00Z')));
}
```
